# 课表与 AI 识图

2026-10-06 新增。用户上传课表图片，由视觉大模型识别成结构化课程，再在本机渲染成周课表。

## 端点与模型

0.4.0 起识别端点内置进构建，正常使用无需填 Key。默认走 `https://ai.123312.xyz/v1` 上的 `deepseek-v4.1-flash`，`reasoning_effort: "high"`、`temperature: 0`、`response_format: json_object`。

端点与 Key 由 `local.properties` 的 `vision.baseUrl` / `vision.apiKey` 在构建时注入 `BuildConfig`，`local.properties` 已被忽略，因此版本库里没有 Key。课表页的高级设置可以覆盖端点、模型或填自己的 Key。

这是一个明确的取舍：**Key 打进 APK 意味着任何拿到 APK 的人都能提取并盗刷额度**。当前是自用分发，接受这一点；若要公开分发，应改为用户自带 Key 或走服务端转发。用户自带 Key 的路径仍然保留，用 Android Keystore AES/GCM 加密存在本机，使用独立别名。

## 请求契约

```
POST {vision.baseUrl}/chat/completions
Authorization: Bearer <BuildConfig.VISION_API_KEY 或用户填写的 Key>
Content-Type: application/json

{"model":"deepseek-v4.1-flash",
 "messages":[{"role":"system","content":"<纯文本规则 + JSON 示例>"},
             {"role":"user","content":[{"type":"text","text":"请识别这张课表图片…"},
                                       {"type":"image_url",
                                        "image_url":{"url":"data:image/jpeg;base64,…","detail":"high"}}]}],
 "response_format":{"type":"json_object"},
 "temperature":0,"max_tokens":8192,"stream":false}
```

约束与实现要点：

- **图片只能出现在 user 消息里**。system/assistant 带图会返回 400，因此 system 保持纯文本。
- JSON 模式要求提示里包含 `json` 字样与完整示例，两者都已写入提示。
- 端点的主机与路径在发请求前校验，Key 不可能被发到其他源；不跟随重定向。
- Key 会先 trim，含 CR/LF 直接拒绝（防请求头注入）；Key 不出现在请求体，也不出现在 `toString()`。

## 响应与渲染

模型返回 `choices[0].message.content`，期望形如：

```json
{"is_timetable":true,"term":"…",
 "courses":[{"name":"…","teacher":"…","room":"…",
             "weekday":1,"start_period":1,"end_period":2,
             "start_week":1,"end_week":16}]}
```

解析层容忍代码块围栏、字段别名（`day`、`course_name`、`instructor`、`classroom`、`start_section`…）与中文写法（`星期三`、`第1-2节`、`1-16周(单)`）。校验层会拒绝越界字段、折叠重复行，并把同一时段不同课程的冲突单独报出。`is_timetable:false` 或课程列表为空时，界面明说没识别到课表且不保存任何内容，模型返回的自由文本原因不会展示给用户。

**单双周是一个独立字段**（`parity`：`ALL` / `ODD` / `EVEN`），不是靠周次范围推断的。同一时段一门单周课加一门双周课是合法课表，不算冲突；只有共用同一奇偶性的重叠才算冲突。

渲染分三层：今日课程列表、按周查看的课表网格、点开单门课看教师与地点。「按周查看」需要开学日期才能算当前周，未设置时按第 1 周显示并提示设置；设置后卡片显示当前周与对应日期区间。

图片在进入请求前会先解码边界、按 2 的幂次采样、缩放到长边 2048 再按质量阶梯压成 JPEG，因此不会触到单图 32 MiB / 8192 px 的上限。

## API Key

内置端点的 Key 在构建时注入 `BuildConfig`（见上）。用户自带 Key 时用 AES/GCM 加密后存在本机，密钥由 Android Keystore 持有，使用独立的 Keystore 别名，删除其中一个不会让另一个失效；不落日志，每次请求按需解密而不是长期缓存。

## 失败处理

以下情况都不会崩溃，也不会留下脏数据：未填 Key、Key 含换行、图片格式不支持 / 为空 / 超限（在本地拒绝，不上传）、400、401/403、402、413、429、3xx、5xx、超时、无网络、200 但内容为空、被截断、内容过滤、非 JSON、响应包结构异常、字段越界、课程冲突。请求被拒时，本机已保存的课表保持不变。

## 验证状态

代码、契约与失败路径由 104 项课表单元测试覆盖（模型与校验、识图客户端、响应解析、持久化、Key 保险库、控制器、图片处理），HTTP 层全部是假的。写这些测试时发现并修掉了三个自身缺陷：星期别名返回了内层下标（`星期三`→2、`sunday`→8）、重复行未折叠、时段冲突被误报成字段非法；单双周最初被静默丢弃，补上 `parity` 字段后才正确。

**已端到端验证**（2026-10-06，模拟器 + 真实接口）：用一张合成的中文课表图片（含 13 门课、单双周标注、合并单元格）走完整流程 —— 选图、上传、识别、渲染、落盘、重装后重新读取。结果 12 门课程全部识别，教师与教室正确（`大学英语 / Sarah Chen / 外语楼205`、`高等数学 / 李国强 / 文理楼301`、`毛泽东思想和中国特色社会主义理论 / 黄凯 / 文科楼202`）。周次筛选经核对正确：双周限定的课在第 1 周不出现，`9-16周` 的课在第 1 周不出现。

**未验证的部分**（不要当成已验证）：

- 拍照入口仅在 API 29+ 提供，只编译通过，未实拍；相册选择是主路径，无需权限。
- 模型识别准确率取决于图片质量与模型本身，一张图通过不代表所有课表都能读对。界面已写明「看不清的内容不会凭空补全」。
- 极窄屏幕（< 360dp）与超大字体的网格排版未逐一比对。

## 分辨率与编码（2026-10-07 修订）

本节取代上面「缩放到长边 2048 再按质量阶梯压成 JPEG」的描述。

### 实测：准确率对上传分辨率极其敏感

同一张真实课表图、同一套提示词、同一个视觉模型（`glm-5v-turbo`），只改上传前的长边尺寸：

| 上传长边 | 识别准确率 |
| --- | --- |
| 1700 px（原图） | 100% |
| 1024 px | 68% |
| 850 px | 48–83% |

结论：**把图压小是识别失败的头号原因，不是模型能力的问题。** 每缩小一次就丢掉一批课程格子的笔画，模型只能猜。因此：

- `VisionImageLimits.TARGET_SIDE_PX` 由 2048 提到 **4096**，贴近端点自己 8192 px 的上限，而不是贴一个「上传方便」的尺寸。
- 上传预算不再手工取 8 MiB，改为从端点单图上限反推（见下），否则 4096 档位下正常照片的 q88 就会被判超预算、被迫降质，等于把分辨率赚来的准确率又赔回去。

这组数字只覆盖一张图、一个模型，代表趋势而不是所有课表的保证；方向和量级足够明确，所以按「宁大勿小」取舍。

### 编码：截图走无损 PNG，照片走 JPEG 阶梯

`TimetableImageLoader` 按字节魔数判断来源（picker 给的 MIME 只是提示，不作为依据）：

- **PNG 且无损编码后仍在预算内 → 上传 `image/png`。** 没有旋转也没有缩放时直接上传原始字节，一个比特都不动；发生缩放或旋转时，对缩放后的像素做 PNG 无损重编码。JPEG 在锐利文字边缘产生的振铃会直接损伤识别，截图正是最锐利的那一类。
- **其余一律回退 JPEG 阶梯**：`88 → 80 → 70 → 55`，**第一档 88 能过就不降**。低质量档位只为「实在塞不下也别整张失败」而存在。
- GIF / WebP / 未识别格式解码后走 JPEG；魔数不完整（截断签名）一律算未识别——宁可走 JPEG，也不要把非 PNG 误判成 PNG 上传。

### 上传预算的不变量

```
MAX_UPLOAD_BYTES = MAX_BASE64_BYTES / 4 * 3 = 25 165 824 字节（24 MiB）
```

24 MiB 原始字节 base64 之后正好是 32 MiB，也就是端点单图上限（`rejectionReason` 用 `>` 比较，边界值本身通过）。这条推导由测试钉住：预算值本身、预算 +1 会被端点拒绝、预算大小的图片 `rejectionReason` 返回 `null`，以及「4096 × 3072 的稠密文字按约 1 字节/像素在 q88 下仍装得下」——最后一条正是 8 MiB 预算会踩的坑。

### 内存有界

- 解码前按 2 的幂次采样，长边**不会**越过 `TARGET_SIDE_PX`；解码后还会再 `fitInside` 兜一次。
- `BitmapFactory.decodeByteArray` 抛 `OutOfMemoryError` 时不再崩进程：`prepare` 内部把它转成 `ImagePreparationException`（沿用「这张图片太大…」文案），上层不需要改。`loadPreparedImage` 里原有的 `catch (OutOfMemoryError)` 保留作兜底。

### 验证状态

新增 18 项纯 JVM 单测（魔数识别 3、PNG/JPEG 选择 4、预算不变量 2、JPEG 阶梯 4、采样边界 2、内存兜底 3）。这些用例用变异测试逐个确认过会失败：预算改回 8 MiB、PNG 预算差一个字节、PNG 签名放宽、阶梯去掉 88 档、采样放宽到 2 倍目标、OOM 兜底失效 —— 六种改法都被对应用例抓到，没有只会永远通过的断言。

**未验证**：真实 PNG 截图与真实照片的端到端识别没有在本机重跑；「PNG 无损比 JPEG q88 更准」这一点来自 JPEG 在锐利文字上的振铃机制，没有和 1700 px 那组一起单独实测，所以它是推断而非实测结论。

## 两个独立故障与原始证据（2026-10-07 补记）

上一节把识别失败归因于分辨率，本仓库另一处注释把归因于「模型把预算烧在推理上」。**两者都对，但它们是两个独立的故障**，需要分开陈述，否则任何一处单独读起来都会被另一处推翻。

### 故障一：默认模型在密表图上永远不会给出答案

真机抓包（同一张 1700×710 真实课表图，`https://ai.123312.xyz/v1`）：

| 请求 | 结果 | 耗时 |
| --- | --- | --- |
| `deepseek-v4.1-flash` + `reasoning_effort: high` | `finish_reason=length`，`completion_thinking_tokens=8192`，`content` 为空 | 40 s |
| 同上，`medium` / `low` / 不带该参数 | 三种都一样：思考吃满 8192，`content` 为空 | 38–44 s |
| 同上，`max_tokens` 16384 / 32768 | **HTTP 499**（网关 60 秒硬超时） | 60 s |
| 同上，`stream: true` | 8194 个 chunk 全是推理，`content` 仍为空 | 39 s |
| **`glm-5v-turbo`** | `finish_reason=stop`，思考 0 token，8 门课全中 | **11 s** |

`reasoning_effort` 在这个端点上对这个模型不起作用，`max_tokens` 又抬不上去（网关 60 秒），所以它是**必失败**而不是「偶尔不准」。这个失败在应用里表现为 `EMPTY_RESPONSE`（「AI 没有返回识别内容，请重试。」），换多少张图都一样——因为图片越密、思考越久。

据此默认模型改为 `glm-5v-turbo`，`deepseek-v4.1-flash` 降为第二选择，而且只在**没得到任何结论**的失败上触发（空回答 / 超时 / 5xx）。模型已经看过图并给出结论时（包括「这不是课表」、解析失败、限流）不换模型重试：换一个模型解决不了「答得不好」，限流则会再撞一次同一道墙。

每次尝试有自己的 40 秒上限。没有它的话，第一次尝试会一直占着，等外层 90 秒看门狗兜底时第二次尝试只分到不到一秒——回退恰恰在最慢的场景里失效。

### 故障二：模型答得出来时，准确率随上传分辨率急剧下降

同一张图、同一套提示词、同一个 `glm-5v-turbo`，只改上传前的长边：

| 上传长边 | 准确率（40 个字段） |
| --- | --- |
| 1700 px（原图） | 98–100%（8 门课 7–8 门完全精确） |
| 1024 px | 68% |
| 850 px | 48–83% |

所以「宁大勿小」：目标边长 4096，且长边超过端点 8192 px 上限的来源**不允许**走原始字节直传——`resized` 只描述解码后的位图，一张 1080×20000 的长截图会采样成很小的位图（看起来没缩过），而真正上传的字节仍然是 20000 px，端点会拒绝且没有任何回退接住它。这条由 `mayPassThrough(rotationDegrees, resized, sourceSide)` 判定并被单测钉住。

### 提示词

改成先朗读星期列（`day_headers`）与节次行（`period_labels`），再逐块抽取；并按本校自己的行标签解读节次——`上午1-5` / `下午6-9` / `晚上10-13` 一律取末尾数字，模型不会再把下午重新从 1 数。同一张图实测从 83%（一版提示词）提到 98%（三版提示词）。`day_headers` / `period_labels` 只是让学生把两个轴真的读一遍，解析侧不消费它们。

试过但**没有**采纳的一版：让模型把据以判断的上下行标签原文抄进 `start_period_label` / `end_period_label`，由应用自己换算。实测与纯数字完全一致（连错的那一门都一样），说明残差是「看错了色块下沿」而不是「数错了行」，多两个字段只是多花 token。

### 节次只有 1–13，「无节次」不再是概念

早期版本把「无节次」行建成节次 0 并单独一行渲染。用户要求删除：落在这一行的课**从第 1 节开始**。现在课表里不存在节次 0：

- 提示词明确要求节次只写 1–13，不要写 0；无节次行的课填 1。
- 解析侧兜底：模型若把该行标签原样答成 `"无节次"`，或仍然写 0，都会被认出「这一行没有节次号」。
- 核心校验器把任何 0 或负数钳到 1，而不是判 `INVALID_FIELD`——后者会让一整张课表报废，代价远大于一行节次不准。

**落位不是简单地钉死在 1。** 如果那一天的上午 1 已经有课，把无节次的课也写到第 1 节就会与它冲突，而冲突同样会报废整张课表。所以无节次的课落在该星期**第一个没有被别的课占用的节次**：当天第 1 节空着就是 1（常见情况，也是用户要的行为），被占用就顺延。它永远参与不了「让整张表失败」这件事，而用户仍然看得到这门课、并且可以手动把它挪到正确位置。占用判定只看同一星期，并且尊重单双周——单周课与双周课共用同一个节次本来就不冲突，不会被当成占用。

### 识别结果可手动修改

识别准确率再高也不会 100%，所以结果不再是一次性的：课程详情面板可进入编辑，字段包括课程名、教师、上课地点、星期、起止节次、起止周与单双周；管理卡片可手动新增一门课。保存走同一条 `TimetableValidator`，冲突与越界在那里报错并原样显示给用户，已有课表在校验失败时不被改动。编辑被拒时会清掉页面上残留的识别失败卡片：那张卡的标题是「没识别到课表」，让一条关于手填字段的消息挂在那标题下会指错方向。
