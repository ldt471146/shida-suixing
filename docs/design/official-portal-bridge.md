# 学校原网页认证

2026-10-06，用户在红米 K80 的 GXNU-YC 上确认 0.2.1 仍显示「学校认证配置响应无法解析」，并明确要求软件转接原网页：填入已保存账号、密码，选中供应商，点击登录。

0.2.2 将正常认证交给学校自己的网页和脚本。原生首页、账号安全存储、连接动画、结果提示和自动连接开关沿用现有模块。软件等待真实表单及其提交处理函数就绪，填写可见字段并只点击一次登录。它不再以本地解析 loadConfig 成功作为提交账号的前置条件。

已只读核对学校真实 mobile.js / pc.js：登录表单为 f1，字段为 DDDDD 和 upass，供应商选择器为 ISP_select，登录按钮为 0MKKey。相同字段还出现在隐藏的备用 f0 中，因此只操作可见登录表单。表单 onsubmit 调用学校的 ee(1)，由学校代码执行正常 JSONP 认证；不能调用 form.submit()。

所有学校网页资源与登录请求由当前目标 Wi-Fi 的 Android Network 创建连接，限定学校 HTTPS 域名和端口。外站、注销及不支持的提交方式不会携带账号。WebView 仅在本次连接期间创建；密码注入使用安全的字符串编码，不写诊断日志。学校 store 保存登录信息时改用当前页面内存，尝试结束销毁网页及临时状态。

是否联网仍由同一 Wi-Fi 的 HTTPS 204 检查决定。学校页面提示成功、显示在线模板或登录按钮消失，都不能单独作为联网成功的证据。账号被拒、页面需要验证码、加载超时和无法联网保留明确反馈与人工网页入口。

验证覆盖真正执行填表脚本的异步加载、供应商选择、特殊密码、重复轮询、隐藏备用表单及退出按钮；HTTP 层覆盖原 Wi-Fi 绑定、GB18030 / UTF-8、压缩、重定向、请求范围及取消。编译和内存测试不能替代 K80 的真实认证。最终验证记录和安装包将在实际检查后追加。

## 0.2.3 内嵌登录页

用户在真实校园网反复失败后要求直接内嵌学校登录页。0.2.3 把学校原页面显示在 App 内，「学校认证页面」入口不再跳系统浏览器：

- 页面由 `VisiblePortalSession` 承载，与自动认证共用 `PinnedPortalResources` 和 `portal-bridge.js`。所有资源与登录请求仍绑定当前 GXNU-YC 的 Android Network，仍限定学校 HTTPS 域名，仍只允许同源 GET。
- 打开后自动触发一次填表与提交，与隐藏流程完全一致；提交后不再重复点击。
- 顶层提供返回与「重新加载」。自动提交未成功或学校要求验证码时，用户可直接在这个页面手动输入并点击学校自己的登录按钮，无需离开 App。
- 关闭页面即销毁 WebView、清空 Cookie 存储并结束资源。凭据仍只来自 App 的安全存储，页面不会把账号带到其他网络。
- 当前网络不是 GXNU-YC、或账号与供应商未设置时，入口不打开页面，给出明确提示，避免把凭据提交到错误的网络。

模拟器已验证入口守卫行为、页面布局与无崩溃启动；`yc.gxnu.edu.cn` 在虚拟 Wi-Fi 下不可达，真实表单自动填写与提交仍需在实体手机上确认。

## 0.3.0 登录后返回

内嵌页面此前没有收尾动作：登录成功后页面就停在那里，用户不知道该怎么回到 App。0.3.0 补上完成流程：

- 页面打开期间，按**同一个 Wi-Fi** 轮询外网验证（间隔 2 秒，总截止 60 秒，在 IO 线程执行）。成功判据沿用原有的 HTTPS 204 检查，没有引入新的成功信号——学校页面自己提示成功不算数。
- 认证成功后显示「认证成功，校园网已可上网」，约 1.5 秒后自动返回 App，同时提供「完成」按钮可立即返回，不让人干等。
- 失败或超时保留原因提示，页面继续可用于手动登录，不会把用户堵死。
- 返回后首页读取真实状态，在线就是在线；关闭页面会取消轮询并销毁 WebView 与临时 Cookie。
- 打开页面的前置守卫不变：只有当前网络是 GXNU-YC 且账号与供应商都已设置时才打开，否则给出明确提示，避免把凭据送到错误的网络。

模拟器上已验证入口守卫与页面渲染；真实登录后的自动返回路径需要在实体手机上确认（模拟器连不上学校域名）。
